# Выкладка на VM

Сервер — **один статический бинарник без зависимостей**: фронтенд вшит внутрь
через `go:embed`, базы данных нет, состояние партий живёт в памяти процесса.
Поэтому выкладка сводится к «скопировать файл и перезапустить сервис».

Есть два пути. Выберите один.

---

## Путь 1. systemd (рекомендую: проще и легче)

### Что нужно на VM

Ubuntu/Debian, 1 vCPU, 512 МБ памяти, nginx. Go на сервере **не нужен** —
бинарник собирается у вас на машине.

### Первая установка

На своей машине:

```bash
make package            # соберёт dist/siege-linux-amd64.tar.gz
```

Для ARM-машины (Ampere, Graviton, Oracle Cloud free tier):

```bash
make package ARCH=arm64
```

Копируем и ставим:

```bash
scp dist/siege-linux-amd64.tar.gz user@ваш-сервер:/tmp/
```

```bash
ssh -t user@ваш-сервер 'mkdir -p /tmp/siege-pkg && tar xzf /tmp/siege-linux-amd64.tar.gz -C /tmp/siege-pkg && cd /tmp/siege-pkg && sudo ./deploy/install.sh'
```

Скрипт создаёт системного пользователя `siege`, кладёт бинарник в
`/opt/siege`, конфиг в `/etc/siege.env`, ставит и запускает unit, после чего
проверяет живость.

### Обновление

Одной командой с вашей машины:

```bash
make deploy HOST=user@ваш-сервер
```

Собирает, прогоняет тесты, копирует, перезапускает сервис. Партии,
идущие в этот момент, прервутся: состояние хранится в памяти. Выкладывайте,
когда никто не играет, или предупредите игроков.

### Управление

```bash
sudo systemctl status siege
sudo systemctl restart siege
journalctl -u siege -f           # логи
/opt/siege/siege -health         # быстрая проверка
```

## Путь 2. Docker

```bash
scp -r . user@ваш-сервер:/srv/siege     # или git clone на сервере
ssh user@ваш-сервер
cd /srv/siege
cp .env.example .env && nano .env
docker compose up -d --build
docker compose logs -f
```

Контейнер слушает только `127.0.0.1:8080` — наружу его выставляет nginx.
Образ собран на distroless, запускается не от root, файловая система
только для чтения.

## nginx и TLS

Одной командой на VM, из того же распакованного пакета:

```bash
sudo ./deploy/setup-tls.sh ваш-домен ваша@почта
```

Скрипт проверит, что домен действительно указывает на эту машину, поставит
nginx и certbot, выпустит сертификат, подставит домен в конфиг nginx и в
`/etc/siege.env`, перезапустит сервис и проверит, что сайт отвечает по https.
Запускать повторно безопасно.

Порядок внутри важен и руками его легко перепутать: сертификат выпускается
**до** установки нашего конфига, потому что конфиг ссылается на файлы
сертификата, которых до этого ещё не существует.

Если делаете руками — конфиг лежит в [deploy/nginx.conf](../deploy/nginx.conf),
в нём надо заменить `siege.example.com` на свой домен.

**Важно для SSE.** Состояние партии сервер шлёт потоком Server-Sent Events.
Если прокси буферизует ответ, игроки увидят ход соперника с задержкой в
минуты. В конфиге это уже учтено, не убирайте:

```nginx
proxy_buffering off;
gzip off;
proxy_read_timeout 1h;
proxy_set_header Connection "";   # keep-alive до бэкенда
```

Сервер со своей стороны шлёт `X-Accel-Buffering: no` и пингует поток
комментарием раз в 20 секунд.

## Настройки

Все через переменные окружения — см. [.env.example](../.env.example).
Для systemd это `/etc/siege.env`, для Docker — `.env`.

| Переменная | По умолчанию | Зачем |
|---|---|---|
| `SIEGE_ADDR` | `:8080` | адрес прослушивания |
| `SIEGE_ALLOWED_ORIGIN` | пусто | **поставьте свой домен** в проде: отсекает POST с чужих сайтов. Схема должна совпадать с реальной: `http://` или `https://` — иначе игроки получат «запрос с чужого источника» |
| `SIEGE_LOG_FORMAT` | `text` | в проде `json` |
| `SIEGE_LOG_LEVEL` | `info` | |
| `SIEGE_MAX_ROOMS` | `200` | предел комнат в памяти |
| `SIEGE_ROOM_TTL` | `2h` | когда убирать брошенные комнаты |
| `SIEGE_TURN_TIMEOUT` | `0` (выкл) | автозавершение хода, например `120s` |
| `SIEGE_BOT_DELAY` | `350ms` | пауза между действиями бота, пока люди видят, что он делает; `0` — без пауз, не больше `5s` |
| `SIEGE_SHUTDOWN_WAIT` | `10s` | сколько ждать активные запросы при остановке |
| `SIEGE_ICE_SERVERS` | публичный STUN Google | серверы ICE для голосовых звонков, JSON-массив |

`PORT` тоже уважается — если захотите положить это на хостинг, который
задаёт только его.

## Голосовые звонки

Звук идёт **напрямую между браузерами** (WebRTC): на сервере нет ни
медиапотоков, ни лишних портов. Сервер только перекладывает сигналы
соединения через тот же SSE, которым ходит партия. Нагрузка на VM от звонков
практически нулевая.

Но два требования к окружению жёсткие:

**1. Только HTTPS.** Браузер не даст доступ к микрофону по `http://` —
исключение лишь `localhost`. Если TLS настроен по инструкции выше, всё в
порядке; при раздаче по голому HTTP кнопка звонка честно скажет, что нужен
https.

**2. STUN обязателен, TURN желателен.** По умолчанию используется публичный
STUN Google — он сообщает браузеру его внешний адрес. Этого хватает
большинству домашних сетей. Но если кто-то из игроков сидит за симметричным
NAT (часто в корпоративных и мобильных сетях), прямое соединение не
установится, и нужен **TURN** — ретранслятор трафика.

Свой TURN проще всего поднять на той же VM через
[coturn](https://github.com/coturn/coturn):

```bash
sudo apt install coturn
# /etc/turnserver.conf: listening-port=3478, lt-cred-mech,
# user=siege:СЕКРЕТ, realm=siege.example.com
sudo systemctl enable --now coturn
```

И прописать его в конфигурации сервиса:

```bash
SIEGE_ICE_SERVERS='[{"urls":"stun:stun.l.google.com:19302"},{"urls":"turn:siege.example.com:3478","username":"siege","credential":"СЕКРЕТ"}]'
```

Учтите, что TURN гоняет через себя весь звук: три собеседника — это примерно
100–150 кбит/с в каждую сторону. Для самой дешёвой VM это заметно, но
терпимо.

Проверить список, который уезжает в браузер:

```bash
curl -s https://siege.example.com/api/meta | python3 -m json.tool | grep -A5 iceServers
```

## Что проверить после выкладки

```bash
curl -s https://siege.example.com/healthz          # {"status":"ok",...}
curl -s https://siege.example.com/version
curl -N https://siege.example.com/api/rooms/XXXXX/events   # поток не должен обрываться
```

Откройте сайт в трёх вкладках, создайте комнату в одной и войдите по коду
в двух других: партия должна начаться автоматически.

## Ограничения, о которых стоит знать заранее

**Состояние — в памяти одного процесса.** Это осознанный выбор: партия живёт
полчаса, игроков трое, база данных только усложнила бы установку. Следствия:

- перезапуск сервиса обрывает идущие партии;
- **масштабировать на несколько инстансов нельзя** — игрок попадёт не в тот
  процесс. Если это понадобится: либо sticky-сессии по коду комнаты в nginx,
  либо вынести состояние в Redis и слать события через pub/sub.

Один процесс спокойно держит сотни одновременных партий: на комнату уходит
несколько килобайт и одно соединение SSE на игрока.

**Переподключение.** Токен игрока лежит в `localStorage`, код комнаты — в
адресе страницы. Если игрок закрыл вкладку, он вернётся в ту же партию по
той же ссылке, пока комната не истекла по `SIEGE_ROOM_TTL`.

## Если что-то не работает

| Симптом | Куда смотреть |
|---|---|
| 502 от nginx | сервис не поднялся: `journalctl -u siege -n 50` |
| Ходы соперников «залипают» | буферизация SSE в прокси — проверьте `proxy_buffering off` |
| `запрос с чужого источника` | `SIEGE_ALLOWED_ORIGIN` не совпадает с доменом (без слэша на конце!) |
| `слишком много запросов` | встроенный лимит 30 POST за 10 секунд на IP |
| Комната пропала | истёк `SIEGE_ROOM_TTL` или сервис перезапускали |
| Комната не создаётся, в ответ 404 | в конфиге nginx `location` для API заканчивается слешем: на `POST /api/rooms` nginx отвечает 301 и уводит на несуществующий путь. Нужен префикс `/api/` |
| Кнопка звонка говорит про https | сайт открыт по http — нужен TLS |
| «Соединяем…» и не соединяется | нет TURN, а игрок за симметричным NAT |
| Микрофон не спрашивают | разрешение уже отклонено в настройках сайта в браузере |
